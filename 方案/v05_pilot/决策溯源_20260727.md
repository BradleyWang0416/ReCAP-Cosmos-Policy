## 二、决策序列

### 第一阶段：评估方法

#### D1 — 只读文档判断进度，还是另行验证语义？

| 备选 | 成本 | 否决/采纳 |
|---|---|---|
| A. 依据 5 份验收报告 + CHANGELOG 判断 | ~1 h | ❌ |
| B. A + 独立验证字段语义与检索有效性 | ~半天 | ✅ |

**依据**：v04 的审计器审的是**形式正确性**——partition 间 SHA 零交集、receipt 完整、`future_rows_read=0`、数值有限。它审不了**语义正确性**——这个字段真的是人手吗？这个检索真的有用吗？所有阶段都标 `PASSED`、guardrail 全零，只读文档必然复述其结论。

**后果**：这是 P0-1 与 P0-4 被发现的唯一原因。若选 A，本次评估会得出「进展顺利，补完 RECAP 训练即可」。

#### D2 — `action` 字段的语义：信任 manifest，还是直接读原始 HDF5？

选择直接读。结果：`action` 与 `end_position` 同轴相关性 0.971 / 0.975 / 0.880，恒等映射 R² = 0.930，中位残差 6.4 mm；与真人手腕位置的最大相关性仅 0.613 且需换轴。

**决定性的一步是导出图像目视确认**：`human_camera` 确实是人手操作、`robot_camera` 是机械臂，两者帧对齐。这一步把结论从「几何通道错了」精确成「**视觉分支是真人类信号，几何分支不是**」——后续所有关于视觉/几何分工的判断都依赖这个区分。

#### D3 — 发现 P0-1 后：立即建议改代码，还是先做定量对照？

选先对照。**依据**：换通道的代价是阶段 1 全部重做 + 重训 2 个方法（约 74 GPU·小时）。这个量级的决策应当建立在数字上，而不是「读代码发现映射写错了」。

### 第二阶段：P0-1 定量对照

#### D4 — 变体 B（真人手）的坐标映射方案

| 备选 | 实测 | 否决/采纳 |
|---|---|---|
| 逐 pool-episode 标定 | 最准 | ❌ 需要该 pool episode 的机器人数据，违反 human-only 边界；只能作 oracle 参考 |
| 逐 episode 相似变换 | R² = 0.650，残差 60.8 mm | ❌ 测试时不可实现 |
| 全局相似变换（绝对位置） | R² = 0.146，残差 119 mm | ❌ 太差 |
| **全局标定，只拟合位移增量的旋转+尺度** | R² = 0.059（拟合集） | ✅ 采纳 |

**依据**：`align_pool_chunk` 只使用位移增量，平移自动抵消，因此只需要旋转和尺度；且这两个量只能在 seen-train 上拟合（那里同时有人手和机器人），符合协议。

**代价（已在结论中声明）**：变体 B 的判别力很差——query 内候选距离 std 仅 0.049，而 A 为 0.233。**这是我的构造缺陷，不是通道本身的缺陷**。B 通道的 oracle 上界在 K=8 时为 7.6 mm（基线 11.1 mm），说明信息存在，缺的是表征。这一区分直接决定了 E2 必须按 B1→B4 的阶梯继续试，而不是就此判死真人手通道。

#### D5 — 对照使用哪些 query？

选择复用 `stage4_smoke_plan.json` 里那 160 个已冻结的 dev query，而非重新抽样。**依据**：保证比较的是管线真实使用过的窗口，杜绝「换了抽样所以结论不同」的质疑。

#### D6 — 人手夹爪代理如何确定？

24 点手部骨架无官方文档。选择数据驱动识别：在 **seen-train** 上计算所有点对距离与 `gripper_state` 的相关性，取最高者，得到点对 (16,20)，|corr| = 0.822。

**依据**：只用 seen-train 识别拓扑（一次性结构发现，等同于读 README），不碰 held-out，避免循环论证。

### 第三阶段：检索消融

#### D7 — 消融是否纳入预测时域 K？

**触发点**：时基核查发现 `step` 逐帧 +1、标称 30 fps，即 **H=8/K=8 ≈ 0.27 秒**，该窗口内机器人平均只移动 11.1 mm。

选择纳入 K ∈ {8,16,32,64}。**这是本次会话信息量最大的单个决定**：K 成为第一主导变量，现生产配置的 ρ 从 1.19（K=8）变到 0.74（K=64）。若不扫 K，结论会停在「检索是负收益」，而错过「只要改 K 就能翻正」。

#### D8 — 视觉分支：接受 16 维 WAN 的结论，还是测更强的特征？

| 备选 | 否决/采纳 |
|---|---|
| A. 直接判定「WAN 空间均值太粗糙，需要更高维」 | ❌ 未经检验的归因 |
| B. 加测 576 维稠密灰度描述子，区分「维度不够」与「方向错了」 | ✅ |

**结果**：576 维同样差（ρ 1.32–1.75），且 `geom+vis`、`geom+pix` 在**每一个 K** 上都劣于 `geom` 单独使用。

**后果**：结论从「维度问题」变为**方向问题**——query 是机器人图像、candidate 是人手图像，任何**当前帧外观**描述子的主导信号都是具身外观差而非任务状态。这直接决定了 E3 必须上具身不变的语义特征（DINO/SAM），而不是提高分辨率。

#### D9 — 是否继续 `recap_hand_ret` 训练？

选暂停。**依据**：K=8 下现配置 ρ = 1.19，意味着交给 RECAP 的残差目标**比 baseline 的绝对目标更难**。此时训练无论结果如何都无法归因——方法、通道、时域、检索规则四个因素纠缠在一起。

#### D12 — 探索期的 Docker 纪律

会话中的诊断脚本跑在宿主机 Python 上，违反 v04 §2.2 的 Docker-only 约束。

| 备选 | 否决/采纳 |
|---|---|
| A. 要求一切进容器 | ❌ 会使已完成的诊断全部作废，且只读 CPU 分析进容器无实际收益 |
| B. 忽略该约束 | ❌ 等于取消规范 |
| **C. 分成类别 A / B** | ✅ |

采纳方案：**类别 A**（只读、纯 CPU、不加载模型权重、不产生性能声明）允许宿主机运行，但须标记 `NONFORMAL_DIAGNOSTIC`、公开披露，**且结论进入 v05 冻结协议前必须在容器内复算一次**；**类别 B**（其余全部）仅限容器。

#### D13 — v05 的 GPU 策略

v04 要求显式提供恰好四个 GPU 编号。改为**按张数声明**（E1/E2/E5 需 0 张、E3 需 1 张、E4 需 4 张），启动器从空闲卡自动选择，回执记录实际分配的 **GPU UUID**。

**依据**：编号会随其他用户的作业变化，复现应锚定 UUID 而非编号；且强制绑定编号会在共享机器上造成无谓等待。

#### D14 — E1 的评估集

选 seen-validation，而非 v04 的 final 集。**依据**：打开 final 会迫使 v05 重新划分 final 集。已写入总计划 §3.3 作为硬纪律。

### 第五阶段：工程与文档

#### D15 — GPU 能否加速 E1/E2？

用户提问触发实测：

| 项 | 实测 |
|---|---|
| 运动学字段读取 | 9 KB/episode，0.4 ms |
| E1.3 最大变体的距离运算 | ~7×10¹¹ flops → 208 核 CPU 约 3 分钟，4090 约 15 秒 |

**结论：不能。** E1/E2 是 I/O 与 Python 循环受限，不是算力受限。

**但由此产生一个更有价值的调整**：GPU 的作用不是让 E1/E2 更快，而是**解锁 E3（DINO/SAM），从而扩大 E2 的选项集**——B4 是 E2 中最可能过线的一档。而 E3 只需 **1 张卡约半小时**，不必中断占用 6 张卡的 LlamaFactory 作业。四卡组留给 E4。

#### D16 — 优化范围：全部改，还是先测？

先测。实测 `d12` = 0.94 s、`d13` = 1.45 s → **不动**。只改 `d14`/`d15`/`d16`。避免了无收益的回归风险。

#### D17 — 描述子改写：更快，还是逐位一致？

| 备选 | 否决/采纳 |
|---|---|
| A. 积分图池化（快得多） | ❌ 改变浮点求和顺序，破坏与已记录数字的逐位一致 |
| **B. `imgs.mean(-1, dtype=np.float32)` 替代 `astype().mean()`** | ✅ 已验证逐位相同，且省掉每 episode 约 330 MB 临时数组 |

#### D18 — GEMM 精度：float32 还是 float64？

选 float64。float32 快一倍，但 `abs-pos` 等特征的近距离候选可能因舍入翻转排序。既然验收标准是「输出不变」，精度不能让步。

#### D19 — worker 数量

实测：读取可扩展到 16+ worker（10.7×，2149 MB/s），但 block-mean 描述子内存受限，16 worker 比 8 worker **慢 2.7×**。

但同一配置两次实测为 4.3 s 与 17.7 s（共享节点，数十用户）。**决策：不按噪声数据卡「最优」值**，取拐点内的 8 并保留 `PILOT_WORKERS` 覆盖，理由写进 docstring。

#### D20 — 文档更正方式

| 文档 | 性质 | 处理 |
|---|---|---|
| `方案/v04/CHANGELOG.md` | 只追加 | 追加更正条目，登记新旧对照，**不改写既有条目** |
| 偏差记录、PILOT_LOG、总计划 | 可修订 | 直接改正，并在 CHANGELOG / §七 登记 |

#### D21 — E1 与 E2 的执行顺序

初始表述漂移（清单写「先做 E1 + E2」，后续口头说「下一步 E2」）。经用户指出后更正为 **E1 → E2**。

**依据**：E2 的判据本身引用 E1 的输出——「在 E1 选定的 K 下，某档达到 ρ ≤ 0.85」。成文时该限定词遗漏，会使 E2 可在最有利的 K 上挑点通过。这是比顺序更严重的缺陷，已修复。

**校准信息**：已有消融中 B 通道 ρ 在 K=8/32/64 上为 0.96/0.96/0.95，近乎不随 K 变化，故 B0 的否决结论不依赖 E1；但 B1–B3 是新表征，不得假定同样平坦。

## 四、本会话的三处自我更正

1. **P0-1 数字口径**：把单 episode / held-out 子集的数字误标为 48-episode 汇总。把 P0-1 主证据重写为可复现脚本 `d02` 并实跑后更正（相关性 0.940/0.960/0.797 → 0.971/0.975/0.880；R² 0.913 → 0.930；与人手腕最大相关性误记 0.82 → 0.613）。**结论方向未变且更强。**
2. **姿态列范围**：「四个 held-out 任务全程恒定 (180,0,90)」只对抽查 episode 成立；16 个 seen 任务并不恒定（`action` 178 个唯一值、`end_position` 1567 个）。held-out 集上 orientation 次要指标接近退化的推论保留，须在 v05 评估设计时复核。
3. **E1/E2 顺序与 E2 判据**：见 D21。

三处均已同步进相关文档，其中 CHANGELOG 以追加条目方式登记新旧对照。

        │
        ├─ D9 暂停 recap_hand_ret 训练
        │
        ├─ D10 v04 无法修订 → 换版本号

        │   D14 评估集限定 seen-validation
        │

**最终形态**：一份 403 行的 v05 探索期总计划，包含

- **通用规范（§二）**：Docker 边界与 A/B 分级、离线与禁止降级、路径与资产登记、GPU 按张数声明、实时日志、原子落盘与断点续跑、变更记录与文档同步；

- **E0–E6 六个环节**，各带判据、否决条件与当前状态；
- **E2 的否决条件**：若 B1–B4 在 E1 选定的 K 下全部无法达到 ρ ≤ 0.90，判定 Human2Robot 不适合作为替代数据集，转为换数据集或重新定位课题。
