# 本地 ↔ 远程服务器 协作流程

## 〇、本文件是什么

记录本项目在**两台机器上并行开展**时的文件组织与同步约定：什么走 git、什么走 rsync、什么永远不传、实验在哪台机器上启动、结论从哪里读。

- 它**不是**实验方案。E0～E6 的目标与判据见 `方案/v05_pilot/RECAP_Human2Robot_v05探索期执行总计划.md`。
- 它**不是**结果记录。带基线的数字一律写入 `方案/v05_pilot/PILOT_LOG.md`。
- 它记录**工作怎么流转**，以便任何一次改动都能明确回答"改的是哪台机器、同步了没有、结果从哪看"。

机制落地提交：`cfda4ca`。脚本位于 `tools/sync/`，简要用法另见 `tools/sync/README.md`（本文件是完整版）。

## 一、问题的形状

项目同时存在于两处：

| | 路径 | 角色 | 能力 |
|---|---|---|---|
| 本地 | `/home/cc/wxs/ReCAP-Cosmos-Policy` | 读代码、写文档、分析结果 | 有 Claude Code，无 GPU，无数据集 |
| 远端 | `wxs:/home/wxs/ReCAP-Cosmos-Policy` | 跑训练与评测 | 有 GPU 与全部数据 |

三类东西**无法**在两处同时存在：

1. **数据集与权重** —— `/DATA1/wxs/DATASETS/Human2Robot/`（1316 个 hdf5）、`/DATA1/wxs/ReCAP_M5B_*_RUNS/` 下的 checkpoint。体积决定了不可能同步。
2. **仓库内的软链接** —— 共 7 条，全部指向仓库外的远端路径（见 `元信息/软链接清单.md`），在本地是断链。
3. **容器内路径** —— `.venv/bin/python` 指向 `/home/cosmos/.local/share/uv/...`，只在 docker 容器 `recap_m5b_p2_formal` 内有效，**宿主机上是断链**。

若只用一层 git 同步源码，本地就完全看不到实验产出，任何判断都要逐次 ssh 现取，上下文严重残缺。本方案的目的是在不搬运大文件的前提下补回这份上下文。

## 二、三层结构

| 层 | 内容 | 传输方式 | 入 git | 落地位置 |
|---|---|---|---|---|
| **A 源码** | `.py` / `.md` / `.json` / 配置 | git，双向，经 GitHub | ✅ | 仓库本体 |
| **B 镜像** | 远端产出的**小文件**：日志、metrics、eval 结果 | `pull_mirror.sh`，远→本地**单向** | ❌ | `.mirror/` |
| **C 元信息** | 大文件的**描述**：软链接指向、目录体量、HDF5 字段、episode 数 | `gen_meta.sh` 生成，随 git 走 | ✅ | `元信息/` |

设计要点：

- **B 层让远端产出变成本地真实文件**。日志与 metrics 落到本地后可直接 Read/Grep/diff/跨文件比对，这是与"每次 ssh 现取"的本质差别——后者只能看到你当时想到要看的那一个文件。
- **C 层让传不动的东西仍以可读形式存在**。判断"action 是几维"不需要数据集本身，只需要 schema。
- **B 层单向**。`.mirror/` 是快照，不是工作副本；`pull_mirror.sh` 带 `--delete`，本地改动会被覆盖。

当前体量：B 层 2001 个文件 / 34MB；C 层 4 个文件 / 16KB。

## 三、安装（每台机器一次）

```bash
tools/sync/install_hooks.sh
```

把 `core.hooksPath` 指向 `tools/git-hooks/`，使 pre-commit hook 随 git 同步（见第七节）。

本地另需两项 ssh 配置（已在 `~/.ssh/config` 完成，此处备查）：

- `Host wxs` 开 `ControlMaster auto` + `ControlPersist 10m`，连接复用后单次 ssh 由 675ms 降至 10ms；
- `Host github.com` 显式指定 `IdentityFile /home/cc/wxs/.ssh/id_ed25519`。GitHub 认的是这把 ed25519 密钥，`id_rsa` 无效；此前依赖 ssh-agent，在无 agent 的 shell 中会失效。

## 四、日常流程

### 4.1 拉取远端结果

```bash
tools/sync/pull_mirror.sh              # 增量，幂等，随时可重跑
tools/sync/pull_mirror.sh --dry-run    # 只看会传什么
```

### 4.2 改代码 —— 一律改本地

对话中的所有编辑作用于 `/home/cc/wxs/ReCAP-Cosmos-Policy/`。**改完服务器上仍是旧代码**，必须显式同步。

### 4.3 同步到远端

```bash
git add -u && git commit -m "..." && git push
ssh wxs 'cd /home/wxs/ReCAP-Cosmos-Policy && git pull --rebase'
```

### 4.4 启动实验 —— 一律在远端

```bash
ssh wxs 'cd /home/wxs/ReCAP-Cosmos-Policy && \
  V05_PILOT_GPU_COUNT=4 V05_PILOT_GPU_DEVICES=0,1,2,3 \
  nohup bash start_v05_pilot_docker.sh > /tmp/pilot_launch.log 2>&1 &'
```

`nohup ... &` 不可省——ssh 断开会杀掉前台进程。长训练用 tmux 更稳：

```bash
ssh wxs 'tmux new -d -s pilot "cd /home/wxs/ReCAP-Cosmos-Policy && bash start_v05_pilot_docker.sh"'
ssh wxs 'tmux capture-pane -pt pilot | tail -30'
```

### 4.5 刷新元信息

数据集或软链接变动后：

```bash
tools/sync/gen_meta.sh
git add 元信息 && git commit -m "刷新元信息" && git push
```

## 五、一个完整例子

以 `.mirror/V05_PILOT/orchestrator_logs/pilot_session_20260727T135409Z_2753596/` 为例。

**① 拉取**：`tools/sync/pull_mirror.sh` 后，该目录 8 个文件全部落到本地。

**② 离线读**。`status.json`：

```json
{"run_id": "pilot_session_20260727T135409Z_2753596", "attempt": 1,
 "status": "COMPLETED", "exit_code": 0,
 "started_at_utc": "2026-07-27T13:54:09Z", "finished_at_utc": "2026-07-27T13:54:12Z"}
```

配合 `attempt_0001.command.txt`（`V05_PILOT_GPU_COUNT=1`、`V05_PILOT_ALLOW_NETWORK=0`）可判定：这是单卡、离网、耗时 3 秒的 preflight，不是训练。**整个判断过程无需 ssh**——因为跨文件比对本身就需要文件都在手边。

**③ 改代码**：编辑本地 `tools/human2robot_v04_retrieval.py`。

**④ 同步**：`git push` + 远端 `git pull --rebase`。

**⑤ 重跑**：ssh + nohup 启动，回到 ①。

闭环的关键在于 ① 和 ② 之间没有 ssh——**结论是从本地文件读出来的**。

## 六、边界规则

### 6.1 镜像有白名单和大小保险丝

`tools/sync/sync.conf` 中：只拉 `.json/.jsonl/.yaml/.log/.txt/.md/.csv/.tsv/.toml`，且单文件不超过 `MIRROR_MAX_SIZE=2M`，并排除 `checkpoints/`、`iter_*`、`wandb/` 等目录。

因此以下情况需要动作：

| 情况 | 处理 |
|---|---|
| 新开输出目录（如 `ReCAP_M5B_V06_RUNS`） | 加入 `sync.conf` 的 `MIRROR_ROOTS`，否则拉不到 |
| 某日志超过 2M | ssh 直接 `tail`/`grep`，或临时调高 `MIRROR_MAX_SIZE` |
| 产出为 `.npy` / `.pkl` | **不要**加进白名单。在远端写脚本 dump 成 json 再镜像，更省带宽也更可读 |

配置集中在 `sync.conf`，改配置不要改脚本。

### 6.2 `.mirror/` 只读

不入 git，会被 `--delete` 覆盖。要改变产出，改产生它的代码（A 层）。

### 6.3 两端提交一律 `git pull --rebase`

不要用默认 merge。曾因此产生合并提交 `8533837`，且把 `.gitignore` 的内容整段重复贴了一遍。

若在服务器上同时开着 Codex 会话，此规则尤其重要——本机制落地当天就出现过两端并发提交。

### 6.4 元信息采集用宿主机 anaconda

`sync.conf` 的 `META_PYTHON=/home/wxs/anaconda3/bin/python`（自带 h5py 3.12.1）。**不能**用仓库的 `.venv/bin/python`——它只在容器内有效，采集走 ssh 直连宿主机。

## 七、pre-commit hook

`tools/git-hooks/pre-commit` 自动把仓库内软链接写入 `.gitignore` 并取消其跟踪，已纳入版本控制，改动随 git 同步。

原 `.git/hooks/pre-commit`（已改名 `.superseded` 留档）有两处缺陷，现版本已修复：

1. **`grep -qS` 中 `-S` 不是合法 grep 选项**，每次执行返回 exit 2，`!` 取反后判定恒为真，于是每次 commit 都无条件重复追加一遍条目。`.gitignore` 因此由 69 条有效规则膨胀至 293 行，其中 7 个条目各重复 4 次。现改用 `git check-ignore` 判定——它是 Git 自身的忽略逻辑，还能识别 `.venv/` 这类父目录规则，因此 `.venv/bin/python` 之流不再被冗余写入。
2. **`for link in $SYMLINKS` 按空格分词**，含空格的路径会被截断。现用 `find -print0` 读取，中文与空格路径均安全。

服务器实测：修复后连续 commit，`.gitignore` 稳定在 108 行不再增长。

## 八、速查

| 我想…… | 做什么 |
|---|---|
| 看最新实验结果 | `tools/sync/pull_mirror.sh`，然后读 `.mirror/` |
| 知道某 hdf5 有哪些字段 | 读 `元信息/HDF5结构样本.json`，不必 ssh |
| 知道某任务有多少 episode | 读 `元信息/数据集清单.md` |
| 知道某软链接指向哪 | 读 `元信息/软链接清单.md` |
| 改代码并在远端生效 | 本地改 → `git push` → 远端 `git pull --rebase` |
| 起训练 | ssh + `nohup` 或 tmux，见 4.4 |
| 看 GPU 占用 | `ssh wxs 'nvidia-smi'` |
| 加一个要镜像的目录 | 编辑 `tools/sync/sync.conf` 的 `MIRROR_ROOTS` |

一句话：**代码在本地改 → push/pull 同步 → ssh 起训练 → `pull_mirror.sh` 拉回结果 → 本地离线读。大文件不动，只同步它的描述。**
